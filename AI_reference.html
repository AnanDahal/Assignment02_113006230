Entry 1 – Two-pass AABB Tile Collision

Location:

assets/Script/MarioBundle.js, lines 891–960 (_moveX() and _moveY() methods of the Player class)

Problem:

Mario was occasionally getting stuck in corners when running along a wall. The player would stop moving even when pressing a direction key with no visible wall in front.

Prompt used: 
I have a Mario game where the player uses AABB tile collision. When running against a wall and jumping, Mario sometimes gets stuck at the corner of a tile. I'm currently applying both X and Y position corrections in a single pass. How should I fix this?
AI Response (summary):

Claude explained that combining horizontal and vertical resolution in a single pass causes the corner-sticking bug. It recommended separating into two passes: move X first and resolve horizontal collisions, then move Y and resolve vertical collisions independently. This way the horizontal and vertical velocities don't interfere with each other.

Refinement & Explanation:

I split my existing collision code into _moveX() (lines 891–919) and _moveY() (lines 921–960). In _moveX(), I check left-column or right-column tiles against all tile rows the player occupies, and push the player out horizontally. In _moveY(), I do the same for up/down. I kept my own tile-boundary math (Math.floor(this.x / T)) and only changed the structure to two sequential passes. The upward collision check (lines 930–945) also triggers question block and brick-breaking logic which I wrote myself.

Entry 2 – Rotated Sprite Frame Rendering

Location:

assets/Script/MarioBundle.js, lines 188–204 (drawFrame() method, specifically the f.rotated branch)

Problem:

Some sprite frames were appearing stretched or in the wrong position. After inspecting the plist file I noticed some frames had textureRotated: true, but my drawing code wasn't handling that case.

Prompt used: 
In my Cocos2D plist sprite sheet, some frames have textureRotated = true. My drawImage call uses sw and sh from the plist rect, but the rotated sprites look wrong. What's the correct way to draw a rotated sprite frame from a texture atlas using canvas?
AI Response (summary):

Claude explained that when a frame is rotated 90° in the atlas, the width and height are swapped in the source texture. To draw it correctly you must: (1) swap sw and sh in the drawImage source parameters, (2) translate to the bottom-left of the destination, (3) rotate the canvas by -Math.PI/2, then draw.

Refinement & Explanation:

I added the rotated branch at lines 196–199. I had already written the non-rotated path; I only added the ctx.translate / ctx.rotate / ctx.drawImage sequence for the rotated case after Claude confirmed what the correct transform should be. I verified this against a few frames in the plist to make sure the positions were correct.

if (f.rotated) {
    ctx.translate(0, dh);
    ctx.rotate(-Math.PI / 2);
    ctx.drawImage(sheet.img, f.sx, f.sy, f.sh, f.sw, 0, 0, f.sh * sc, f.sw * sc);
}

Entry 3 – Web Audio API Autoplay Policy

Location:

assets/Script/MarioBundle.js, line 260 (AudioContext creation), line 333 (resumeCtx()), lines 1652 and 1800 (call sites on user input)

Problem:

Background music was not playing when the page loaded. No errors appeared in the console – the audio just stayed silent until the user clicked something, and even then it didn't always start.

Prompt used: 
My Web Audio API BGM doesn't play on page load in Chrome. I create an AudioContext and call start() on a buffer source but nothing plays. No error in console. Why?
AI Response (summary):

Claude explained Chrome's autoplay policy: AudioContext is created in a "suspended" state and must be resumed after a user gesture (click, keypress, etc.). It suggested calling audioContext.resume() inside a user input handler before playing any sound.

Refinement & Explanation:

I added the resumeCtx() method (line 333) which calls this.ctx.resume() on the existing AudioContext I had already created. I then call it at the first Enter/Space keypress in the menu (line 1652) and at game start (line 1800). The BGM and SFX were already working correctly once the context was resumed – I only needed to add this single resume call.

resumeCtx() {
    if (this.ctx.state === 'suspended') this.ctx.resume();
}

Entry 5 – Cocos Creator 2.4.8 Project Wrapping

Location:

assets/Script/MarioBundle.js, lines 2611–2650 (hideCC(), getOrCreateCanvas())
assets/Script/MarioBundle.js, lines 2587–2609 (injectModal(), injectUserInfo(), injectControls())
project.json, assets/Scene/main.fire, assets/Script/MarioBundle.js.meta

Problem:

The assignment required submitting a Cocos Creator 2.4.8 project. I had a complete working vanilla HTML5 Canvas game but was unfamiliar with CC's internal project structure (.fire scene files, .meta files, plugin script format). After getting the project to open in CC, two further bugs appeared:

  • The game canvas was offset downward — a large black gap appeared above it in CC preview.
  • The login modal was not clickable — it appeared but clicks went through to the canvas behind it.
Prompt 1 (project structure): 
I have a vanilla JS HTML5 Canvas game and need to wrap it in a Cocos Creator 2.4.8 project. What files are required (project.json, .fire scene, .meta)? I want my JS to run as a plugin script before CC initializes.
AI Response 1 (summary):

Claude described the required CC 2.4.8 file structure and explained that a script in assets/Script/ with "isPlugin": true in its .meta file is injected as a global <script> tag before CC starts. It also explained the minimal .fire scene format needed to satisfy CC's scene requirement.

Prompt 2 (canvas positioning bug): 
In CC preview my canvas is positioned too low — there's a big black gap above it. I'm using position:fixed; top:50%; transform:translate(-50%,-50%) but it's not centering. Works fine outside CC.
AI Response 2 (summary):

Claude diagnosed that CC 2.4.8 applies a CSS transform to <body> for its own preview scaling. Elements with position: fixed inside a transformed element are positioned relative to that ancestor, not the viewport. The fix: append the canvas wrapper to document.documentElement (the <html> element) instead of document.body, since <html> is never transformed by CC.

Prompt 3 (modal z-index bug): 
My login modal appears but I can't click any buttons inside it. The game canvas is below it visually but clicks seem to go to the canvas. How do I fix this?
AI Response 3 (summary):

Claude identified that the canvas wrapper had z-index: 99999 and pointer-events: auto on the canvas itself, while the modal had a lower z-index. Even though the modal appeared on top visually, the canvas was intercepting clicks. Fix: raise the modal z-index above the canvas wrapper.

Refinement & Explanation:

For the canvas positioning fix, I changed all document.body.appendChild calls to document.documentElement.appendChild (lines 2591, 2599, 2608, 2630). I understood this was fixing a CC-specific behavior and verified it worked in preview. For the modal fix, I raised #loginModal's z-index from 200 to 9999999 in the CSS string at line 2554. I chose 9999999 to ensure it stays above all game UI layers. I had written the rest of the modal HTML, CSS, and auth logic (lines 1593–1660) myself; only the z-index value was changed based on AI advice.
